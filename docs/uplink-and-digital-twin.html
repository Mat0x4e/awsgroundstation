Uplink testing with AWS Ground Station and the digital twin

protogroundstation - compiled 18 November 2026 - account 471112743408, region eu-central-1

Summary

A real uplink to a public satellite through AWS Ground Station is not possible. Public broadcast satellites are downlink-only, and AWS transmits only in S-band (2025-2110 MHz), where no public satellite listens.

The digital twin can rehearse the control plane (scheduling, configs, events, automation) without antenna time or spectrum licensing. It moves no radio signal and no data.

None of the other uplink-capable satellites works with AWS Ground Station either: their uplink frequencies are outside the AWS S-band range. A real uplink through AWS Ground Station needs your own (or a partner's) S-band satellite, onboarded and licensed.

Terminology

Two categories of satellite in AWS Ground Station
CategoryDefinitionOnboarding procedure
Public broadcast satellites (PBS) AWS's own term: satellites with a public, downlink-only direct-broadcast path that AWS has validated. Aqua, Terra, SNPP and JPSS-1/NOAA-20 in the user guide; NOAA-21 in practice. On request, through the Satellite Onboarding Questionnaire, for the ground stations you name. Not enabled by default.
Operator-authorized satellites (non-PBS) Our term; AWS has none. Any other satellite, including ones whose data is public. AWS documentation treats it as "your satellite". Full onboarding: NDAs, technical validation, per-site spectrum licensing, and the satellite operator's authorization.

"Public data" does not mean "public downlink": a satellite whose products are freely published is not PBS unless AWS lists it.

Other uplink-capable satellites: why none works with AWS Ground Station

AWS Ground Station transmits only between 2025 and 2110 MHz and receives only in S-band and X-band (7750-8500 MHz). Every option below falls outside those ranges. On top of that, an AWS uplink requires the satellite to be onboarded by (or on behalf of) its operator, with a spectrum licence per site.

Amateur LEO satellites (ISS, SO-50, AO-91, AO-73, SONATE-2...) 145 / 435 MHz (some 29 MHz) 145 / 435 MHz Uplink and downlink are both far below the AWS S-band and X-band ranges. Transmitting also requires a licensed amateur operator and callsign, which is not how AWS licenses its sites.
QO-100 (Es'hail-2, geostationary) 2400-2410 MHz 10489-10499 MHz The uplink is about 290 MHz above the AWS uplink band (2025-2110 MHz), and the downlink is above the X-band receive range (8500 MHz). Same amateur-licence requirement.
Iridium L-band, ~1616-1626.5 MHz Same band Outside both AWS ranges. It is also a closed commercial network: only Iridium-certified modems can transmit, and traffic goes through Iridium's own gateways.
Argos / Kineis UHF, ~401 MHz Delivered through CLS / Kineis ground processing Outside the AWS ranges. Only certified transmitters are allowed, and the data is processed by the operator's ground segment, not by a customer ground station.
Eutelsat OneWeb Ku-band (~14 GHz) Ku-band (~11 GHz) Outside the AWS ranges. It is an internet service through the operator's own approved terminals, not a satellite a third-party ground station can address.

How such an uplink would be verified

AWS Ground Station cannot hear these satellites, so it cannot confirm an uplink to them. The confirmation would come from receivers outside AWS:

  • APRS digipeaters (ISS, SONATE-2): the relayed packet appears on aprs.fi and ariss.net.
  • FM and linear transponders: listen to the downlink while transmitting (full duplex), or check a recording of the pass on the SatNOGS network.
  • QO-100: watch your signal on the public BATC / AMSAT-UK WebSDR at Goonhilly.

None of these uses AWS Ground Station, which is why they are out of scope for this project.

2. What we will test with the digital twin

The digital twin provides copies of every AWS Ground Station location, named Digital Twin <station>, with the same capabilities, site masks and coordinates. It returns the same API responses and emits the same EventBridge events as production. It has been generally available since August 2024 in every region where Ground Station runs.

Test scope

  1. Scheduling: ListContacts, ReserveContact and CancelContact for the async (DigIF to S3) and sync (demod/decode to EC2) mission profiles, with production-like contention.
  2. Config regression: deploy Terraform changes to mission profiles, configs and dataflow endpoint groups, and confirm contacts are still offered. The two defects that left the sync profile with 0 contacts (missing dataflowEndpointRegion; re-serialised demod/decode JSON) took manual trials against production. The twin would catch this kind of defect without touching production.
  3. Event-driven chain: PREPASS event to receiver_arm Lambda, receiver EC2 start, SSM arm, listener bind; then COMPLETED event to Step Functions, IAM permissions and CloudWatch alarms.
  4. Timing: receiver arm sequence against the mission profile pre-pass duration.
  5. Contact lifecycle against dataflow endpoints: endpoint group handling during a synthetic contact.
  6. Uplink control plane (exploratory): whether an S-band AntennaUplinkConfig + UplinkEchoConfig mission profile can be created and scheduled. This depends on AWS's answer.

3. Limits of the digital twin test

Validated

  • API calls and responses
  • Mission profile and config acceptance
  • Contact scheduling and contention
  • EventBridge events and the automation they trigger
  • IAM, Lambda, EC2, Step Functions, alarms

Not validated

  • Any radio transmission, uplink or downlink
  • Payload data: no dataflow delivery, nothing reaches S3 or EC2
  • Telemetry: not supported on twin stations
  • Packet format of the sync egress, frame sync, RT-STPS, CSPP
  • Link budget, elevation and weather effects
